# Мой планер — Telegram-бот

Личный планер в Telegram (задачи, привычки, цели, заметки) для Оли и Мамы —
двух пользователей, ID которых зашиты в переменную окружения `USERS`.
Весь код бота — один файл `bot.py` (~1000 строк), ярус T0.

## Архитектура

Задачи/привычки/цели хранятся в Google Sheets: у каждого владельца свой
недельный лист («📅 Оля 01.09–07.09» и т.п.), создаваемый дублированием
шаблона `📅 Неделя` (колонка = день недели, фиксированные диапазоны строк
под категории работа/личное/дом и под привычки), плюс отдельный лист целей
на владельца (`🎯 Цели Оля`), тоже дублируемый из шаблона `🎯 Цели`. Голос
расшифровывается через Groq Whisper, текст разбирается в структуру через
Groq LLaMA (`parse_task`) и пишется в нужный лист/ячейку. Отдельно есть два
режима свободной записи с общей клавиатурой-переключателем: «💡 Идеи для
постов» (лист `IDEAS_SHEET`, обрабатывается вручную через content-agent,
эта сборка её не трогает) и «📝 Заметки» (лист `NOTES_SHEET`) — сюда
надиктовывается любой сумбур. Заметки каждый вечер забирает ночной агент
(`run_daily` в 16:00 UTC): берёт все новые записи по каждому владельцу,
прогоняет через LLM, которая сама выбирает форму результата (план/письмо/
список), шлёт готовый текст владельцу в Telegram и помечает заметки
обработанными.

## Ключевые функции ночного агента

- `get_new_notes_by_owner()` — читает лист «📝 Заметки», возвращает
  заметки со статусом «новая» по владельцам, отсортированные по дате/времени.
- `run_nightly_job(context)` — коллбек `job_queue.run_daily`. Для каждой
  заметки сначала пробует разобрать её тем же `parse_task`, что и живой
  голос/текст, и разложить через `_file_parsed_note` прямо в
  задачи/привычки/цели (те же `add_task_to_sheet`/`add_goal`, что и
  обычная запись). Всё, что не задача/цель/привычка (или не удалось
  сохранить, например категория уже заполнена на день), уходит вторым
  куском через `structure_notes_for_owner` — свободный текст произвольной
  формы. Обе части складываются в одно сообщение и уходят владельцу в
  Telegram; помечаются обработанными только те заметки, что реально
  вошли в то, что успешно отправилось.
- `split_into_telegram_chunks(text, limit)` — режет текст на сообщения
  ≤4096 символов по границам абзацев (жёстко по символам, если абзац сам
  длиннее лимита).

## Квота Google Sheets API

`get_sheet()` кеширует открытую таблицу на весь процесс (раньше
переоткрывал её — отдельное чтение по квоте — на каждый вызов любой
функции с таблицей). Отдельно `_retry_on_quota` оборачивает
`gc.request` — низкоуровневый метод, через который в итоге идут вообще
все операции gspread (get/update/append_row/open_by_key/...) — коротким
повтором (макс. ~1.3 сек суммарно) при 429 "Quota exceeded". При
нескольких участниках и нескольких фоновых заданиях (веб-дашборд
каждые 5 минут, ночной агент, вечерний чек-лист) лимит 60 чтений/минуту
на сервисный аккаунт реально исчерпывается — именно так один раз
пропал вечерний чек-лист (429 тихо проглатывался без повтора).

**Важно про длительность повтора:** весь бот вызывает gspread
синхронно прямо из async-обработчиков, без выноса в отдельный поток
(кроме дашборда, см. `asyncio.to_thread` в `build_dashboard_data`) —
поэтому `time.sleep()` в ретраях блокирует ВЕСЬ бот, а не только
текущий запрос. Задержки в `_retry_on_quota` нарочно короткие: длинный
экспоненциальный бэкофф здесь означал бы зависшие на десятки секунд
кнопки у всех участников одновременно при устойчивом исчерпании квоты —
это уже проверялось и отменено. Если квота будет исчерпываться часто —
следующий шаг не увеличивать задержки, а сокращать сам объём чтений
(например, реже обновлять дашборд или кешировать его данные дольше).

## Уведомление о перезапуске

`notify_users_about_restart(app)` шлёт всем из `USER_NAMES` короткое
сообщение при каждом старте процесса (после `app.updater.start_polling`
в `main_async`) — напоминание прислать `/start`, потому что клавиатура
Telegram кешируется на клиенте и не подтянет новые кнопки сама.
Побочный эффект: срабатывает на любой рестарт процесса, не только на
осознанный деплой (например, на аварийный перезапуск Railway) — это
осознанный компромисс, не баг.

## Переменные окружения

Из `.env.example`: `TELEGRAM_TOKEN`, `GROQ_API_KEY`, `SPREADSHEET_ID`,
`GOOGLE_CREDENTIALS_JSON`. В `.env.example` также указан `ALLOWED_USERS`,
но реальный код (`bot.py`) его не читает — вместо этого использует
`USERS=telegram_id_1:Имя1,telegram_id_2:Имя2` (см. `_parse_users`); при
заведении `.env` использовать именно `USERS`, `.env.example` в этом месте
устарел.

## Запуск и деплой

Локально: `pip install -r requirements.txt`, затем `python bot.py`
(нужен заполненный `.env`). Деплой — Railway, автодеплой из GitHub `main`
(push в `main` → Railway сам пересобирает и перезапускает).

**Важно:** НЕ запускать `python bot.py` локально, если бот уже поднят на
Railway — два одновременных экземпляра конфликтуют через Telegram long
polling (это реально уже случалось в проекте). Перед локальным запуском
для отладки — остановить/приостановить деплой на Railway.

**Известное ограничение:** модель ночного агента — Groq
`openai/gpt-oss-120b` (`NIGHT_AGENT_MODEL` в `bot.py`) — временное решение,
пока нет платного ключа Anthropic API. Когда ключ появится, меняется
только реализация `structure_notes_for_owner`, остальной код ночного
агента (`get_new_notes_by_owner`, `mark_notes_processed`,
`run_nightly_job`, `split_into_telegram_chunks`) трогать не нужно.

## Команды

| Команда | Что делает |
|---------|------------|
| `pip install -r requirements.txt` | Установить зависимости |
| `python bot.py` | Запустить локально (см. предупреждение выше про Railway) |

## Удаление записи по голосу/тексту ("удали ...")

`find_matching_entries` ищет по пересечению слов между запросом и
текстом задачи — дата в запросе используется только чтобы выбрать
день, а не для сопоставления. Запрос вида «удали 16 ноября» (без
описания самой записи) поэтому ничего не находит по смыслу: слова
"16"/"ноября" не встречаются в тексте задач. Запасной вариант —
`get_day_candidates(date_str, owner)`: если содержательный поиск не
дал совпадений, но дата распознана, показываем список того, что есть
в этот день, вместо «не нашла». Найдено 13.09.2026 после серии
неудачных попыток удалить/поправить одну и ту же запись через голос
(см. коммит).

**Известный пробел:** фразы-редактирования («исправь запись X на Y»,
«поменяй дату на...») не распознаются как отдельное намерение — в
`parse_task` нет типа "edit", такая фраза либо уходит в "delete" (если
есть слово «удали»/«исправь» иногда матчится как unclear), либо
сохраняется как новая задача с этим текстом дословно. Если это будет
происходить часто — стоит добавить тип "edit" в `parse_task` и ветку
обработки в `process_text`, а не чинить точечно.

## Как здесь работает Autopilot

Сборка ведётся навыком `/autopilot`. Требования, спецификация и таски — в `.autopilot/`.
Прогресс — `.autopilot/dashboard.html`. Правило: требование из `manifest.md`
может снять только пользователь.

Если работа продолжается — скажи «продолжи автопилот»: состояние поднимется
из `.autopilot/state.js`, переспрашивать ничего не нужно.
