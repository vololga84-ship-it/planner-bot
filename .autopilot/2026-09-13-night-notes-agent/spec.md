# Спецификация: Ночной агент обработки заметок

## Задача

У бота-планера есть режим «📝 Заметки» — сумбур, который надиктовывают в
Telegram, чтобы потом причесать в план, ответ на письмо или что угодно ещё.
Сейчас единственный способ получить результат — попросить об этом Claude
Code, а доступ к нему есть только у одной из двух участниц (Оли). Вторая
(Мама) может писать заметки, но никогда не получит из них результат сама.

## Решение

Каждый вечер бот сам, без чьей-либо просьбы, смотрит, у кого за день
накопились новые заметки, сам решает, в какую форму их лучше собрать (план,
черновик письма, список — по смыслу заметок, не по жёсткому шаблону), и
присылает готовый результат прямо в Telegram тому, чьи это заметки. Мама
получает свой результат так же, как Оля — без Claude Code, без чьей-либо
помощи.

Начинка сейчас — модель через уже подключённый Groq (`openai/gpt-oss-120b`,
проверено вживую — заметно сильнее `qwen/qwen3.6-27b`, которая сейчас
разбирает задачи), потому что настоящий Claude API требует отдельного
платного ключа, а такой возможности пока нет (R05i, R03 отложено). Замена
на настоящий Claude в будущем — правка одной функции, не переделка
остального.

## Пользовательские истории

| # | Метка | История | Приёмка |
|---|-------|---------|---------|
| 1 | R01 | Как Мама, я хочу получать причёсанный результат своих заметок в Telegram, не имея доступа к Claude Code | сообщение с результатом приходит в тот же чат с ботом, где она их надиктовала |
| 2 | R02 | Как участница, мои новые заметки из листа «Заметки» обрабатываются каждый вечер сами, без моего запроса | в заданное время бот сам проверяет лист и обрабатывает новые записи каждого владельца независимо |
| 3 | R02.1 | …и если у меня сегодня не было новых заметок — меня не беспокоят зря | владельцу без новых заметок сообщение не шлётся |
| 4 | R04 | Как участница, я хочу, чтобы форму результата (план/письмо/список/etc) выбирала сама модель по смыслу заметок, а не всегда одну и ту же | промпт явно поручает модели выбрать форму; нет фиксированного шаблона в коде |
| 5 | R02.2 | …и если модель не смогла ничего разобрать (сбой Groq, пустой ответ) — заметки не теряются и не помечаются использованными | статус меняется на «обработана» только после того, как результат реально отправлен в Telegram; при сбое заметки остаются «новая» и войдут в следующую попытку |
| 6 | R02.3 | …и если результат длиннее одного сообщения Telegram — я получаю его целиком, а не обрезанным | результат режется на несколько сообщений по границе 4096 символов, а не обрезается |
| 7 | R02.4 | …и если у кого-то очень много (более ~40) новых заметок разом — агент не пытается заглотить всё одним запросом и не падает | при превышении разумного объёма заметки берутся пачкой (see "Решения по реализации"), остаток уходит следующим вечером |

## Решения по реализации

- **Планировщик** — `python-telegram-bot` уже предоставляет `Application.job_queue`; используем `job_queue.run_daily(...)` на фиксированное время (21:00 по времени Екатеринбурга, `UTC+5` → `16:00 UTC`) — почему так: не требует ни отдельного процесса, ни cron на стороне ОС, работает там же, где уже 24/7 крутится бот (Railway), не зависит от того, включён ли чей-либо личный компьютер (see R06i — эта заметка пользователя относится только к отложенной идее R07, здесь не нужна).
- **Модель** — Groq, `openai/gpt-oss-120b`, `temperature` пониже обычного (0.3) — почему так: меньше склонности приукрашивать неясные детали. Известное ограничение: модель может не переспросить про нечётко расслышанное (например, спутанное название), а увереннo придумать деталь — промпт явно требует помечать неясности отдельной строкой, но 100% гарантии для открытой модели такого класса нет; это фиксируется как принятый риск, а не скрывается.
- **Обработка по владельцу отдельно** — каждый владелец (`USER_NAMES`) обрабатывается независимо: сбой или пустой список у одного не должен блокировать другого. Один вызов модели на владельца, с ЕГО заметками за сегодня.
- **Порядок операций** (важно для R02.2) — сначала получить результат от модели → отправить в Telegram → и только при успешной отправке пометить исходные строки «обработана». Если что-то из этого упало — заметки остаются «новая», лог пишется, участник тихо не получает сообщение сегодня (без паники — он не знает, что попытка вообще была, и получит результат завтра вместе с новыми заметками).
- **Разбиение длинных ответов** (R02.3) — резать по границам абзацев на сообщения ≤4096 символов; если единственный абзац сам длиннее 4096 (редкий случай) — резать его жёстко по границе символов на этой длине, без попытки сохранить смысловые границы внутри такого абзаца.
- **Ограничение объёма на один вызов** (R02.4) — лист «Заметки» уже хранит колонки «Дата»/«Время» для каждой строки (см. существующую функцию сохранения заметок); `get_new_notes_by_owner()` возвращает записи, отсортированные по этим двум колонкам по возрастанию. Если у владельца больше 40 новых заметок разом (нештатная ситуация, не обычный день), в обработку берутся первые 40 в этом порядке (самые старые), остальные остаются «новая» и уйдут следующим вечером — почему так: не пытаться угадывать безопасный размер промпта каждый раз, простое жёсткое число дешевле и предсказуемее.
- **Адаптер под будущую замену на Claude (R03, отложено)** — вся работа с моделью — в одной функции `structure_notes_for_owner(owner, notes) -> str`. Когда появится платный ключ Anthropic, меняется реализация этой одной функции; планировщик, работа с таблицей и отправка в Telegram не трогаются.
- **Секреты** — модель обращается к уже существующему `GROQ_API_KEY` из `.env` / Railway. Новых переменных окружения эта сборка не добавляет.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `notes_sheet` (расширение существующих функций работы с листом «Заметки») | чтение/запись листа «📝 Заметки» | `get_new_notes_by_owner() -> dict[owner, list[(row, text)]]`, `mark_notes_processed(rows: list[int])` | структуру листа, лимиты Google Sheets API |
| `night_agent` | логика ночного задания | `run_nightly_job(context)` — коллбек для `job_queue` | порядок «модель → отправка → пометка», разбиение длинных сообщений |
| `llm_structurer` | обращение к модели | `structure_notes_for_owner(owner: str, notes: list[str]) -> str \| None` (`None` — сбой) | какая именно модель/провайдер используется сейчас |

Шов для проверки — тот же `structure_notes_for_owner`: в проверке подменяется
на заглушку, чтобы не дёргать реальный Groq на каждый прогон, а
`run_nightly_job` проверяется с этой заглушкой и поддельными Telegram/Sheets
вызовами (по образцу уже сделанных в этом проекте автономных проверок
маршрутизации — тестовой обвязки в репозитории нет, добавлять её ради
одной ночной задачи непропорционально).

## Вне рамок

| Требование | Почему не сейчас |
|---|---|
| R03 — настоящий Claude через отдельный платный API-ключ | нет возможности завести карту прямо сейчас (R05i); архитектура (`llm_structurer`) собрана так, чтобы это была правка одной функции, когда карта появится |
| R06i — использование личного компьютера пользователя | не нужно для этой сборки — планировщик и так работает на Railway 24/7 |
| R07 — Claude Code, развёрнутый на отдельном сервере | будущая идея пользователя, не запрошена как часть этой сборки |
